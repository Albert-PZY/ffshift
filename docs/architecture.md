# FFShift 架构文档

> 桌面视频格式转换器 · 【2027 届】开发实习笔试交付方案
> v1.0 · 2026-09-22 · 限时 3 天 · 单人 + AI 辅助开发

本文包含：竞品分析、项目命名、技术选型对比、总体架构、模块设计、界面规范、决策记录与排期。
所有选型结论都基于两条约束：**3 天内一个人做完、做好用、能演示**；**生产级标准：稳定 + 低维护**（见 §4.10）。

### 1.3 普遍缺口（机会点）

| 用户痛点 | 现有产品的表现 | 本项目做法 |
| --- | --- | --- |
| 参数看不懂（CRF、码率、preset） | 直接暴露专业参数 | 三档人话预设："更清晰 / 均衡 / 更小" |
| 不知道能不能用显卡加速 | 选项列表里一堆编码器，不知道选哪个 | 自动探测 NVENC/QSV/AMF 并默认推荐可用的那个 |
| 报错看不懂 | 甩出一段 ffmpeg 原始日志 | 翻译成人话 + 给下一步建议，原始日志可展开 |
| 批量体验差 | 加文件、等待、没有进度细节 | 队列 + 速度/剩余时间 + 取消/重试 + 完成通知 |
| 大文件/隐私 | 在线工具要上传、限量 | 全程本地，零上传 |
| 广告与付费墙 | 弹窗、捆绑、水印 | 开源、无广告、无套路 |
| 界面陈旧 | 十年前的视觉与交互 | 极简暗色界面（近单色 + 单一强调色），状态与反馈清晰 |

### 1.4 定位

**给普通人用的本地视频转换器：不用懂参数，也能转好视频。**

三个差异点：
1. **会说人话**：档位化参数 + AI 参数建议 + 报错翻译；
2. **干净**：无广告、无捆绑、无付费墙，开源可查；
3. **顺手**：拖放导入、批量队列、硬件加速自动开。

参考来源：[FileConverter 评测](https://www.appinn.com/file-converter/)、[开源转换工具报道](https://cloud.tencent.cn/developer/article/2611178)、[金舟视频格式转换器](https://www.callmysoft.com/shipinzhuanhuan)、[格式工厂 App 投诉记录](https://tousu.sina.com.cn/complaint/view/17401472793)、[FrameShift](https://github.com/gaurox/FrameShift)。

## 4. 技术选型对比

### 4.1 桌面框架（评审重点）

| 方案 | 技术栈 | 体积/资源 | 客户端能力 | 3 天可行性 | 跨平台扩展 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **Electron** | Node + Chromium | 约 150MB，内存高 | 最成熟：原生窗口/托盘/拖放/文件关联/自动更新 | 高（最省心） | mac 可，移动不可 | ✅ **主选（稳定 + 低维护）** |
| **WPF** | C# / .NET 8 LTS | 小 | Windows 原生能力最强 | 中（现代化视觉打磨慢） | 仅 Windows | ✅ 并列候选（C# 熟手直接选） |
| Tauri 2 | Rust + 系统 WebView | 安装包约 10MB，内存低 | 原生窗口/托盘/拖放/文件关联/自动更新 | 中（Rust 侧可压到很薄） | Windows → macOS 同栈，还支持移动端 | 备选（生态年轻、长期维护面更贵） |
| WinUI 3 | C# + Windows App SDK | 小 | 最"现代 Windows" | 中低（打包与工具链坑多） | 仅 Windows | ❌ 时间风险 |
| Qt 6 QML | C++ | 中 | 高 | 中低（C++ 调试慢） | mac/Linux | ❌（除非已会 Qt） |
| PySide6 | Python + Qt | 打包偏大 | 中高 | 中高 | mac/Linux | ❌ 打包与依赖维护成本高 |
| Avalonia | C# 跨平台 XAML | 小 | 高 | 中 | 跨平台 | 观察项 |
| Flutter desktop | Dart | 大 | 中（桌面插件一般） | 中 | 含移动 | ❌（桌面不划算） |

**决策规则（照做，别纠结）：**
1. 默认选 **Electron**：生产级优先"稳定 + 低维护"——十年以上生态、生产案例多（VS Code / Slack 等）、打包/更新/调试链成熟、会 JS/TS 的人最多，交接最容易；
2. 若你 C# 明显更熟，或明确只做 Windows、想贴公司技术栈 → 直接 **WPF（.NET 8 LTS）**，写进文档当加分项；
3. **Tauri 2 降为备选**：体积和内存更优，但生态年轻、Rust 在长期维护与招人上更贵；只有你已会 Rust 或愿意承担该成本时才选。

### 4.2 FFmpeg 集成方式

| 方式 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| **CLI 子进程** | spawn `ffmpeg.exe`，参数数组传参 | 稳定可控、可取消、可并发、进度结构化 | 需自己解析进度与错误 | ✅ 采用（题意也如此） |
| libav* API | 链接 ffmpeg 库调用 | 细粒度、无进程开销 | 编译/跨平台成本高，3 天做不完 | ❌ |
| 第三方封装库 | fluent-ffmpeg / ffmpeg-python | 少写样板代码 | 多一层黑盒，进度控制不如原生 | ❌ 可不必要 |
| ffmpeg.wasm | 浏览器内跑 | 免安装 | 无硬件加速、大文件内存爆 | ❌（也偏离"客户端"） |

CLI 使用要点：参数一律走数组（不问 shell，防注入、防中文/空格路径问题）；进度加 `-progress pipe:1 -nostats`；取消 = 结束进程；输出后校验文件存在且非 0 字节。

### 4.3 前端框架与 UI 组件

| 框架 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **React + TypeScript** | 生态最大、AI 生成质量最好、资料多 | 需要点工程化习惯 | ✅ 推荐 |
| Vue 3 | 上手快、模板直观 | 生态与类型体验略弱 | 可选 |
| Svelte 5 | 轻、性能好 | 生态小，出问题不好搜 | 不推荐（现在） |
| 原生控件（WPF/Qt 分支） | 一致性最好 | 视觉定制成本高 | 随框架分支 |

| 组件方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **Tailwind + 少量自研组件 + Radix 行为层** | 完全贴合设计规范、无"框架味" | 前期要写基础组件 | ✅ 推荐 |
| Ant Design | 快、组件全 | "后台系统"观感，不像桌面工具 | 不推荐 |
| Fluent UI | Windows 原生观感 | v9 学习成本、定制受限 | 不推荐 |
| 纯手写 CSS | 完全可控 | 3 天里浪费时间 | 不推荐 |

图标用 Phosphor（SVG，禁止 emoji 当图标）；字体 Inter，**打包进安装包本地加载**（桌面应用不能依赖在线字体）。

### 4.4 视频信息与缩略图

| 信息获取方式 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **ffprobe JSON** | 一次拿全：容器/编码/分辨率/帧率/时长/码率/音轨 | 多一次进程调用（毫秒级） | ✅ 采用 |
| 解析 `ffmpeg -i` 的 stderr | 无需额外进程 | 输出格式不稳定，易碎 | ❌ |
| 前端 WebCodecs | 不用起进程 | 格式支持有限、拿不到完整元数据 | ❌ |
| 内嵌封面（attached_pic） | 有海报就用 | 大多数文件没有 | 补充手段 |

| 缩略图方式 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **ffmpeg 抽帧 + 本地缓存** | 格式覆盖全、实现 5 行命令 | 首次导入多一次调用 | ✅ 采用 |
| 九宫格拼图（fps + tile） | 一眼看全片 | 略费时，v1 没必要 | 可选（v1.1） |
| WebCodecs 抽帧 | 不起进程 | 兼容性差、失败率高 | ❌ |

缓存的键用"路径 + 修改时间 + 大小"的哈希，命中直接读图；获取失败的条目不放大灰块占位，改为紧凑行展示（见 §6.2）。

### 4.6 AI 能力接入

| 方案 | 说明 | 优点 | 缺点 | 采用 |
| --- | --- | --- | --- | --- |
| 内置规则引擎 | 关键词 → 参数映射（"微信/发出去"→ 目标体积；"剪辑/上传"→ 1080p H.264） | 离线、零成本、快 | 理解能力有限 | ✅ 必备兜底 |
| LLM API（OpenAI 兼容） | 输入用途文字 + 媒体摘要 + 本机可用编码器 + 预设目录；输出参数 JSON + 一句解释 | 真正"说人话" | 需要 Key、有网络与成本 | ✅ v1 简版（可选） |
| RAG（报错/参数知识库） | 本地检索 ffmpeg 报错与参数说明 | 解释准确、可离线 | 要先攒数据 | v1.1 |
| 本地小模型（Ollama） | 离线跑小模型 | 隐私最好、可当加分项 | 资源占用、体验一般 | 加分项 |

**安全边界（必须做）**：LLM 永远只输出"预设 + 白名单字段"的 JSON，校验通过后才拼接参数；不把视频文件发给任何外部接口；Key 只存本机；调用失败/超时自动降级到规则引擎，不阻塞主流程。

### 4.7 打包与发布

| 方案 | 适用 | 说明 |
| --- | --- | --- |
| **electron-builder（NSIS + 便携版）** | 主选型（Electron） | 一条命令出安装包；electron-updater 做自动更新，链条最成熟 |
| Tauri Bundler（NSIS/MSI） | Tauri 分支 | `tauri build` 出安装包，自带更新器 |
| Inno Setup / MSIX | WPF 分支 | 灵活但多一步 |

备注：未签名 exe 会触发 SmartScreen 提示，README 里说明即可；ffmpeg 二进制用 gyan.dev/BtbN 构建，注明来源与许可（GPL 构建含 x264）。

### 4.8 测试策略

| 层面 | 做法 | 理由 |
| --- | --- | --- |
| 纯函数单测（Vitest） | 参数构造、进度解析、错误映射、目标体积计算 | 高价值、零flake，AI 写起来快 |
| 手动冒烟清单 | 12 条用例（见 `docs/testing.md`）：中文/空格路径、损坏文件、取消、批量、无音轨视频等 | 桌面 UI 的自动化性价比低 |

### 4.9 选型结论与评审话术

**结论：主选 Electron + React + TS（稳定 + 低维护）；C# 熟手直接 WPF；Tauri 2 保留为现代备选。**

三句话解释给面试官听：
1. "它是**真桌面客户端**：原生窗口、托盘、拖放、文件关联、独立安装包，不是浏览器里打开的网页。"
2. "生产级项目优先稳定和低维护：**Electron 生态十年以上、打包/更新链成熟、交接成本最低**；代价是体积偏大，这个取舍我们认。"
3. "ffmpeg 按题目要求走 CLI，但我们用 `-progress` 做**结构化进度**，所以能做取消、重试、批量并发。"

如果面试官追问"Electron 是不是套壳"："它是**独立打包的桌面客户端**：自带运行时、有系统托盘/文件关联/安装与更新体系，VS Code、Slack 都是同路线；我们看的是交付质量与长期维护成本，不是内核形态。"

### 4.10 选型原则（生产级：稳定 + 低维护）

每项选型都按这把尺子量，不接受"炫技型"依赖。

| 原则 | 落地做法 |
| --- | --- |
| 选"无聊"的成熟技术 | 十年以上生态优先于三年新秀；Electron / WPF / React / ffmpeg 都是各自领域最稳的路 |
| 依赖最小化 | 自己能写 50 行就不引小库；引入前先答"它坏了怎么办" |
| 锁版本 | 提交 lockfile；运行时走 LTS/稳定线，不追 beta |
| 人才可得性 | 用 JS/TS、C# 这类招人容易、AI 工具也最熟的栈，方便交接 |
| 更新可控 | 定期小步升级，不跨大版本跳；升级前跑一遍冒烟清单 |
| 数据兼容 | 配置与历史的 JSON 带 version 字段，升级不破坏旧数据 |
| 可观测 | 本地日志 + 错误翻译；出问题能定位，不靠猜 |
| 明确拒绝 | 实验性 API、无维护的库、为省事引入的黑盒封装 |

### 5.1 分层图

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层   React + TypeScript + Tailwind（渲染进程）           │
│  文件列表/缩略图 · 媒体信息 · 档位与设置 · 任务队列 · 日志抽屉    │
├──────────────────────────────────────────────────────────────┤
│ 应用层   TypeScript                                            │
│  状态(Zustand) · 预设映射 · 任务编排 · AI 参数助手 · 错误翻译    │
├──────────── IPC（preload + contextBridge）────────────────────┤
│ 主进程   Electron（薄）                                         │
│  窗口/托盘 · 文件对话框 · 拖放 · 通知 · 设置读写 · 子进程托管       │
├──────────────────────────────────────────────────────────────┤
│ 进程层   ffmpeg.exe / ffprobe.exe（子进程，随包分发）             │

├──────────────────────────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────┘

```

### 5.2 主流程数据流

1. 拖入/选择文件 → 去重、校验类型；不支持的格式直接标"不支持"，不排队；
2. 并发调用 ffprobe（≤3 个）→ 解析 JSON → 列表显示：缩略图 + 文件名 + 时长 + 分辨率 + 大小；
3. 缩略图：`ffmpeg -ss <0.1×时长> -i 文件 -frames:v 1` → 缓存目录；命中缓存不重复抽帧；
4. 用户选档位（或让 AI 给建议）→ 生成参数对象 → 白名单校验 → 入队；
5. 调度器取任务执行（默认同时 1 个；检测到可用硬件编码器可调为 2）；
6. spawn ffmpeg（`-progress pipe:1 -nostats`）→ 按块解析 key=value → 计算百分比/速度/剩余时间 → 事件推给 UI（100ms 节流）；
7. 结束：退出码 0 → 已完成（可打开输出目录）；非 0 → 失败 → 错误翻译 + 保留最后 50 行日志；
8. 设置与历史写 JSON；缩略图缓存按 LRU 清理。

## 6. 关键模块设计

### 6.1 媒体信息（ffprobe）

```bash
ffprobe -v error -print_format json -show_format -show_streams "input.mp4"
```

| 界面展示字段 | 来源 |
| --- | --- |
| 文件名 / 大小 | 文件系统 |
| 时长 | `format.duration` |
| 分辨率 / 帧率 | `streams[video].width/height/r_frame_rate` |
| 视频编码 / 码率 | `streams[video].codec_name / bit_rate` |
| 音频编码 / 声道 | `streams[audio].codec_name / channels` |
| 容器 | `format.format_name` |

只展示能帮用户判断的字段；原始 JSON 折叠在"详情"里备用（实现信息不当主角）。

### 6.2 缩略图服务

- 命令：`ffmpeg -hide_banner -ss <时间点> -i "文件" -frames:v 1 -vf scale=480:-2 -q:v 3 "缓存.jpg"`；
- 时间点取时长 10% 处（<1s 的短视频取 0.1s）；
- 缓存键：`hash(路径 + 修改时间 + 大小)`，放应用缓存目录；抽帧失败记录一次，不重试刷屏；
- 列表里缩略图固定小尺寸（如 96×54），点开详情才显示大图；
- 抽帧失败或未知格式：**不留大灰块占位**，该行用紧凑样式展示，避免"看起来很空很破"。

### 6.3 转换任务引擎

| 项 | 设计 |
| --- | --- |
| 状态机 | `排队中 → 转换中 → 已完成 / 失败 / 已取消`（五种，全局统一用词） |
| 并发 | 默认 1 个任务；检测到可用硬件编码器时允许 2 个；CPU 软编不并发 |
| 进度解析 | `-progress pipe:1 -nostats` 输出 `key=value`；用 `out_time_us` 算百分比，`speed` 算剩余时间 |
| 计算公式 | 百分比 = `out_time / 时长`；剩余时间 = `(时长 − out_time) / speed` |
| 取消 | 结束 ffmpeg 进程 + 清理半成品输出文件 |
| 重试 | 保留原参数重新入队；连续失败 2 次则停止并提供"复制日志" |
| 日志 | 内存保留最后 50 行，失败时展开可见；完整日志落盘 |
| 例外 | 时长未知（部分流）时只显示"已处理时长 + 速度"，不硬算百分比 |

### 6.4 预设 / 硬件加速 / 目标体积

| 档位 | 面向场景 | 参数（示例） |
| --- | --- | --- |
| 更清晰 | 存档、再剪辑 | H.264 CRF 18–20，preset slow，音频 192k |
| 均衡（默认） | 日常使用 | H.264 CRF 21，preset medium，音频 AAC 128k，`+faststart` |
| 更小 | 发手机、省空间 | H.265 CRF 26（或 H.264 CRF 26 + 上限 1080p），音频 96k |

**硬件加速探测（3 步）：**
1. 列出候选：`ffmpeg -encoders` 中找 `h264_nvenc` / `hevc_nvenc` / `h264_qsv` / `hevc_qsv` / `h264_amf` / `hevc_amf`；
2. 真实可用性：对候选逐个试编码 1 秒（`-f lavfi -i testsrc2 -t 1 ... -f null -`），退出码 0 才算可用（列表里有 ≠ 能用）；
3. 缓存结果 + 提供"重新检测"入口；不可用的编码器**直接不显示**（不是灰着）。

**目标体积模式：** 总码率(kbps) ≈ `8192 × 目标MB ÷ 时长(秒)`，再减音频码率。用单遍 ABR（`-b:v Xk -maxrate 1.5Xk -bufsize 2Xk`），界面标注"预计体积"，实际误差 ±10% 属正常（README 说明）。

### 6.5 AI 参数助手

- 输入：用途原文（如"压到 50MB 微信发出去"）+ 媒体摘要 + 本机可用编码器 + 预设目录；
- 输出（JSON，Schema 校验）：

```json
{
  "presetId": "balanced",
  "overrides": { "maxHeight": 1080, "targetSizeMB": 50 },
  "note": "按 50MB 目标压缩，兼容微信发送"
}
```

- 校验失败或调用失败 → 直接用关键词规则出方案，界面不出现报错弹窗（用户无感降级）；
- 结果以"建议方案（可改）"呈现，用户确认后才入队——AI 只给建议，不替用户执行。

### 6.6 报错翻译表（示例）

| ffmpeg 原始信息 | 人话 | 建议 |
| --- | --- | --- |
| `Invalid data found when processing input` | 这个文件读不出来 | 可能没下载完整或已损坏，重新下载或换文件 |
| `moov atom not found` | MP4 文件不完整 | 常见于下载中断的文件，重新下载 |
| `Permission denied` | 输出位置不能写入 | 换输出目录；或输出文件正被播放器占用，先关掉 |
| `No space left on device` | 磁盘空间不足 | 清理空间或换目录 |
| `Unknown encoder 'xxx'` | 该编码器在当前 ffmpeg 里不可用 | 换"均衡/更小"档位重试（自动改用软编） |
| 退出码 1 且无明确信息 | 转换失败（原因不明） | 展开日志看最后几行，或点"复制日志"反馈 |

### 6.7 交互与文案规范（oil-frontend 落地）

按 oil-frontend 的"信息与动作"和"列表与详情"两份契约，本项目固定以下规则：

| 规则 | 落地方式 |
| --- | --- |
| 一个区域只有一个主导动作 | 底部操作区只有「开始转换」是高强调按钮；添加文件/文件夹为次级 |
| 动作文案写清"动作 + 对象" | 用「开始转换」「打开输出目录」，不用「处理」「继续」这类看不清结果的词 |
| 状态词统一五种 | 排队中 / 转换中 / 已完成 / 失败 / 已取消；同一状态只显示一处 |
| 不出现"伪操作" | 不能做的事不摆按钮；硬件编码器不可用就不显示该选项 |
| 低频操作收进"更多" | 重命名、移除、打开所在目录、复制日志进入行内"更多"菜单 |
| 列表只做识别与比较 | 每行：缩略图 + 文件名 + 时长/分辨率 + 一个状态 + "更多"；完整信息放详情抽屉 |
| 危险动作用确认 | 「清空已完成」放在菜单分隔后，二次确认 |
| 报错就地展示 | 行内显示人话原因；原始日志折叠，不占主位 |
| 点击反馈可预期 | 所有可点击区域有 pointer + hover + 按下态；禁用态用 not-allowed |
| 不写废话文案 | 不用文字解释显而易见的流程；标题/按钮/默认值能表达的就不加说明段 |

## 7. 界面规范（ui-ux-pro-max 落地）

> 设计系统已持久化：`docs/design-system.md`（界面实现以该文件为准）。
> 来源与调整：风格、动效、检查清单来自 ui-ux-pro-max 的 **Minimalism & Swiss Style** 条目；暗色底参考其 **Developer Tool / IDE** 调色条目。经检索验证，数据集的现成配色没有可直接套用的"桌面工具 / 暗色 / 极简"条目，故按风格约束做两处标注调整：背景改中性近黑、交互强调色统一为单色蓝、绿色只保留给"已完成"。落地页版式不适用于桌面应用，不采用。

### 7.1 布局与信息结构

单窗口，一次任务流，不用向导：

```
┌────────────────────────────────────────────────┐
│ 顶部栏：FFShift        [添加文件] [添加文件夹]  ⚙ │
├────────────────────────────────────────────────┤
│ 文件列表（主区）                                 │
│ [缩略图] 文件名.mp4   02:31 · 1920×1080 · 82MB │
│           状态 / 进度条 · 速度 · 剩余时间   [⋯] │
│ ……                                             │
├────────────────────────────────────────────────┤
│ 底部操作区：输出位置 | 档位 | [开始转换] | 总进度 │
└────────────────────────────────────────────────┘
右侧抽屉：选中文件的完整信息 + 参数覆盖 + 日志
```

- 空态：一句提示 + 一个动作（「把视频拖进来，或点“添加文件”」），不重复放第二个入口；
- 转换中：行内进度；总进度只在底部出现一次；
- 完成：行内变为「已完成 · 打开输出目录」，托盘通知一次。

### 7.2 视觉规范（摘要，完整见 `docs/design-system.md`）

原则：**颜色不参与分层**。层级用间距、字重和 1px 边框表达；颜色只表达状态和唯一主按钮。

| 项 | 值 |
| --- | --- |
| 风格 | 极简 / 瑞士式：单色为主、留白充足、高对比；必要元素之外全部删掉 |
| 背景 / 表面 | 底 `#0B0C0E`；卡片与面板 `#14161A`；悬停 `#1A1D22` |
| 边框 | 默认 `rgba(255,255,255,.08)`；输入框与次级按钮 `rgba(255,255,255,.16)` |
| 文字 | 主 `#F4F5F7`；次 `#9AA3AE`；禁用 `#565E6B` |
| 强调色（唯一） | 蓝 `#3B82F6`：进度条、选中态、链接、focus ring；hover `#2563EB` |
| 主按钮 | 反白：`#F5F6F7` 底 + `#0B0C0E` 字——整个界面唯一的高强调元素，每屏一个 |
| 状态色 | 已完成 `#22C55E`、警告 `#F59E0B`、失败 `#EF4444`；只出现在状态文字与图标上 |
| 字体 | Inter（本地打包）：正文 13–14px，标题 15–16px/600；数字用 `tabular-nums`；日志与参数用等宽 |
| 间距 | 8px 节奏：4 / 8 / 12 / 16 / 24 / 32；面板内边距 16–24 |
| 圆角 | 控件 8px、面板与弹层 12px、小标签 6px，全站一致 |
| 动效 | 120–180ms ease-out；只做状态反馈；不做滚动动效、不做装饰动画 |
| 图标 | Phosphor 线性 1.5px；16 / 20px 两档；禁止 emoji |
| 可访问性 | 正文对比度 ≥ 4.5:1；focus 可见；状态不只靠颜色表达 |

**明确不做**：渐变、发光/霓虹、第二个强调色、重阴影、装饰插画、滚动特效、emoji 图标、多个高强调按钮、用色块划分区域。

v1 只做暗色主题（当前配色为暗色适配）；亮色主题留 v1.1，避免两套对比度测试拖时间。

### 7.4 直观清晰自检（实现时对照）

1. 层级只用间距、字重、1px 边框；颜色只表达状态与主按钮。
2. 每屏一个主导动作，其余操作降级或收进"更多"。
3. 所有等待都有反馈：队列状态、进度、速度、剩余时间、完成通知。
4. 失败就地给"人话 + 下一步"；原始日志折叠可查。
5. 默认值就是多数人的最优解：档位默认"均衡"，输出默认放到原视频旁的文件夹。
6. 键盘全程可用：Enter 开始、Esc 关弹窗、Tab 顺序符合阅读顺序、focus 可见。
7. 空态只有一句提示 + 一个动作；图片加载失败不留大灰块。
8. 动效只做 120–180ms 的状态反馈；系统开了"减少动态效果"就全部关掉。

## 附录 A：ffmpeg 命令模板

```bash
# 读信息
ffprobe -v error -print_format json -show_format -show_streams "in.mp4"

# 缩略图（快取：-ss 在 -i 前）
ffmpeg -hide_banner -ss 00:00:01 -i "in.mp4" -frames:v 1 -vf "scale=480:-2" -q:v 3 "thumb.jpg"

# 均衡档（H.264 + AAC + 快速起播）
ffmpeg -hide_banner -y -i "in.mkv" -map 0:v:0 -map 0:a? \
  -c:v libx264 -preset medium -crf 21 -pix_fmt yuv420p \
  -c:a aac -b:a 128k -movflags +faststart "out.mp4"

# 硬件加速（NVIDIA 示例；质量参数 cq）
ffmpeg -hide_banner -y -i "in.mp4" -c:v h264_nvenc -preset p5 -cq 23 -b:v 0 \
  -c:a aac -b:a 128k -movflags +faststart "out.mp4"

# 目标体积（单遍 ABR，X = 8192 × 目标MB ÷ 时长 - 音频kbps）
ffmpeg -hide_banner -y -i "in.mp4" -c:v libx264 -b:v 1800k -maxrate 2700k -bufsize 3600k \
  -c:a aac -b:a 128k -movflags +faststart "out.mp4"

# 带进度输出（解析 stdout 的 key=value）
ffmpeg -hide_banner -y -i "in.mp4" -c:v libx264 -crf 21 -c:a aac \
  -progress pipe:1 -nostats -loglevel error "out.mp4"

# 生成测试素材（不用下载）
ffmpeg -f lavfi -i testsrc2=size=1280x720:rate=30 -f lavfi -i sine=frequency=440 \
  -t 10 -c:v libx264 -pix_fmt yuv420p -c:a aac "fixture_10s.mp4"
```

## 附录 B：进度解析与公式

| key | 含义 | 用途 |
| --- | --- | --- |
| `out_time_us` | 已处理时间（微秒） | 百分比：`out_time / 总时长` |
| `speed` | 处理倍速（3.2x） | 剩余时间：`(总时长 − out_time) / speed` |
| `total_size` | 当前输出大小 | 显示"已输出 12MB" |
| `progress` | `continue` / `end` | 判断本次任务结束 |

注意事项：
- 块与块之间以空行分隔，按块解析、按行 `split("=")`；
- 任务刚开始时 `speed` 可能为空或很小，剩余时间先显示"计算中…"；
- 时长未知的流不硬算百分比，只显示已处理时长与倍速；
- 进度更新节流 100ms，别让 IPC 刷爆 UI。
