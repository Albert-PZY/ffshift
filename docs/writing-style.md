# 文案契约 · FFShift

> 所有出口文字都按这份契约写：文档、README、界面文案、提交信息、AI 生成的草稿。
> **上游是 oil-tone**（`github.com/oil-oil/oil-tone`）：一份中文成稿的文风规范，自带 `tone_lint.py`。
> 本文件是它在项目里的落地版——补上项目特有的术语、状态词和提交信息规则，不重复它的通用条款。
> 自动检查有两层：`pre-commit` 调用 oil-tone 的 `tone_lint.py` 检查暂存的 Markdown（FAIL 拦截、WARN 提示）；`commit-msg` 用 `scripts/lib/tone.mjs` 拦提交信息里的空话。

## oil-tone 的红线（摘要，完整规则见 skill 本体）

- 不编造事实、来源、经历与用户反馈；没有来源就不写"业内普遍认为""有研究表明"。
- 不用宣传黑话：`赋能`、`抓手`、`闭环`、`沉淀价值`、`价值落地`。
- 不用模板化领起语与升华结尾：`原因很简单`、`核心问题是`、`综上所述`、`真正重要的是`、`这不仅仅是`。
- 不用含糊动作词：`搞顺`、`跑起来`、`吃下上下文`、`承接需求`、`把内容塞进去`。
- 中文与英文、数字之间留一个半角空格；中文句子用全角标点，代码与路径用半角。

本机装了 skill 就跑自动检查；没装时 `pre-commit` 会打印"文风检查跳过"，不阻塞提交。

写规则说明本身也要过检查：**把禁词放进反引号或代码块**，否则规则文档会被自己的规则拦下（这是实测踩到的坑，见 `docs/decisions.md` ADR-012）。

## 三条底线

1. **具体**：写事实、数字、命令、路径，不写感受。
2. **可核对**：每句话都要能被验证——能指出文件、行号、测试结果。
3. **不空话**：说不出改了什么，就说明还没想清楚。

## 禁词表（出现即回退重写）

优化了性能 · 提升了体验 · 完善了功能 · 修复了一些问题 · 代码优化 · 细节优化
相关调整 · 若干优化 · 整体优化 · 各种优化 · 做了一些改动 · update code · fix bug

## 句式

- 提交首行、标题、按钮：**祈使句**——"修复 X"而不是"修复了 X"。
- 一句话讲一件事，中文 ≤40 字；超过就断句或改表格。
- 数字用阿拉伯数字；单位写全（MiB / 毫秒 / 分钟）。
- 一段不超过 4 行；能用表格就不用段落。
- 中文标点用全角，代码与路径用半角反引号包裹。

## 必须区分来源

写技术判断时标明出处，三者不能混：

| 标记 | 含义 |
| --- | --- |
| 【官方】 | 有文档链接可查（GitHub / git / ffmpeg 等） |
| 【惯例】 | 社区约定，不是官方要求 |
| 【本项目】 | 我们自己的取舍，附理由 |

## 术语统一

| 用 | 不用 |
| --- | --- |
| ffmpeg / ffprobe | FFMPEG、FFmpeg（工具名小写） |
| 缩略图 | 预览图、封面图 |
| 档位（更清晰 / 均衡 / 更小） | 模式、等级、profile |
| 转换 / 转码 | 转格式、压制、encode |
| 队列 | 任务列表、队列池 |

## 状态词（全局只用这五个）

排队中 · 转换中 · 已完成 · 失败 · 已取消

## 自检

- [ ] 有没有可以删掉而不丢信息的句子？
- [ ] 是不是在描述"改了什么"而没写"为什么"？
- [ ] 数字、路径、命令是不是真的核对过？
- [ ] 来源标对了吗（官方 / 惯例 / 本项目）？
