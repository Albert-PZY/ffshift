## ADR-001 · 桌面框架主选 Electron（原选 Tauri 2）

- **日期**：2026-09-22
- **状态**：已接受；同日修订（主选由 Tauri 2 调整为 Electron）
- **背景**：笔试要求桌面客户端（界面选型与"客户端"关联为 0 不考虑）；3 天单人开发；需求方补充"生产级项目要稳定、维护成本低"。
- **决策**：主选 Electron + React + TypeScript；WPF（.NET 8 LTS）为 C# 熟练者的并列候选；Tauri 2 降为备选。
- **备选**：
  - Tauri 2：体积/内存最优，但生态年轻，Rust 在长期维护与招人上更贵；
  - WPF：Windows 原生能力最强，但仅 Windows、现代化视觉打磨慢；
  - Qt 6 / PySide6 / WinUI 3 / Avalonia / Flutter：各有硬伤（调试成本、打包坑、桌面生态弱）。
- **理由**：Electron 生态十年以上、打包/更新/调试链成熟、生产案例多（VS Code / Slack 等）、JS/TS 人才最多，交接与维护成本最低。
- **代价**：安装包约 150MB、内存占用高——作为产品成本接受，并在面试话术中主动说明。
- **反馈**：初版文档主选 Tauri 2，收到"稳定 + 低维护"要求后调整为 Electron，并固化为原则（ADR-008）。实际表现待开发阶段验证。

## ADR-002 · ffmpeg 走 CLI 子进程

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：题目明确可走 ffmpeg 命令行；产品需要进度、取消、重试、批量。
- **决策**：spawn `ffmpeg.exe`，参数数组传参，`-progress pipe:1 -nostats` 输出结构化进度。
- **备选**：libav* API（编译/跨平台成本高）；第三方封装库（多一层黑盒）；ffmpeg.wasm（无硬件加速、大文件内存爆）。
- **理由**：可控性最好——可取消、可并发、进度是结构化 key=value；数组传参避免 shell 注入与中文/空格路径问题。
- **代价**：自写进度解析与错误映射（已模块化设计，配套单测）。
- **反馈**：待开发阶段验证（重点：中文/空格路径、进度准确性）。

## ADR-003 · 缩略图用 ffmpeg 抽帧 + 本地缓存

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：题目第 1 条要求"获取视频缩略图并显示"。
- **决策**：`ffmpeg -ss <0.1×时长> -frames:v 1 -vf scale=480:-2` 抽帧；缓存键为"路径 + 修改时间 + 大小"的哈希，存应用缓存目录。
- **备选**：WebCodecs 抽帧（兼容性差、失败率高）；九宫格拼图（v1 没必要）；内嵌封面（大多数文件没有，仅作补充）。
- **理由**：格式覆盖全、实现简单、可缓存、失败可降级。
- **代价**：首次导入每个文件多一次进程调用。
- **反馈**：待开发阶段验证（重点：抽帧失败不刷屏、不留大灰块占位）。

## ADR-004 · 本地存储先用 JSON 文件

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：需要保存设置与转换历史，且要求低维护。
- **决策**：JSON 文件（带 `version` 字段），v1 不引数据库。
- **备选**：SQLite（查询强，但多一层配置与迁移成本）；localStorage（容量与一致性差）。
- **理由**：3 天成本最低，符合"依赖最小化"；升级不破坏旧数据（version 字段）。
- **代价**：历史量大后需要迁移方案。
- **反馈**：待定。

## ADR-005 · AI 只输出白名单参数 JSON

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：产品需要"一句话配参数"，但不能让模型直接碰命令行。
- **决策**：LLM 输出仅"预设 + 白名单字段 + 一句解释"的 JSON，Schema 校验通过后才拼接参数；无 Key / 超时 / 校验失败自动降级到规则引擎。
- **备选**：让模型直接生成命令行（不可控、存在注入风险）。
- **理由**：安全、可校验、可降级；视频文件与 Key 不出本机。
- **代价**：表达能力受限（对目标用户足够）。
- **反馈**：待开发阶段验证（重点：降级过程用户无感）。

## ADR-006 · 项目命名 FFShift（原 FormatShift）

- **日期**：2026-09-22（同日改选）
- **状态**：已接受；由"FormatShift"改选为"FFShift"
- **背景**：项目要有能讲清、能查重的名字（提交 GitHub）；需求方补充要求"更极客、更方便记忆"。
- **决策**：英文名 FFShift，仓库 `ffshift`；Slogan"ffmpeg 的换挡键"；一句话说明"不用懂参数，也能转好视频"。
- **备选**：FFPilot（AI 副驾）/ Transcodr（黑话去元音）/ VidMogrify（致敬 ImageMagick）/ FFSmith / FFPipe / FFForge；首轮 FormatShift、VidBridge。
- **理由**：FF 是 ffmpeg 系的极客命名传统，Shift 一眼懂"换挡/切换"；7 字符好记好读，仓库名干净。
- **代价**：GitHub 有 1 个无关同名项目（FFShifter，手柄模拟器，0 star）；旧文档已同步改名。
- **反馈**：排除项留档——VidPipe（225 star 同类）/ Remux（行业通用词 + 549 star 同类）/ Molt（6954 同名）/ Smelt（805 同名）/ VidMagick（与手机 App "VidMagic" 读音相同）。

## ADR-007 · 界面走高级极简

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：需求方要求"尽量高级极简、不要花哨、体验优先、直观清晰"。
- **决策**：近中性暗色 + 单一强调色（蓝）+ 反白主按钮；颜色只表达状态和唯一主按钮；明确不做渐变 / 发光 / 装饰插画 / 滚动特效。
- **备选**：多色品牌方案（橙 + 蓝）；亮色优先。
- **理由**：颜色不参与分层，层级靠间距 / 字重 / 边框；减少视觉噪音即减少认知负担。
- **代价**：视觉冲击力弱，靠层次与状态反馈取胜。
- **反馈**：设计系统已按此重写（`docs/design-system.md`），并写入架构文档 §7。

## ADR-008 · 确立"生产级选型原则"

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：需求方要求："生产级项目，尽量使用稳定且维护成本低的技术选型"。
- **决策**：新增架构文档 §4.10 选型原则——选"无聊"的成熟技术、依赖最小化、锁版本、人才可得性、更新可控、数据带 version、可观测、拒绝实验性 API 与黑盒封装；后续每个依赖按此审查。
- **备选**：维持初版"性能 / 体积优先"取向。
- **理由**：长期维护成本 > 短期观感与体积优势。
- **代价**：放弃 Tauri 的体积/内存优势；开发期不能随手引入炫技依赖。
- **反馈**：直接导致 ADR-001 修订；该原则同时适用于代码、依赖与文档工具链。

## ADR-009 · 强制分支模型：main 受保护，改动一律走分支 + PR

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：需求方要求按生产模式管理代码：按模块建分支开发，不允许直接在主分支提交，主分支只能由其它分支合并进来。
- **决策**：`main` 是唯一长期分支，只接受 PR 合并；开发走 `feat|fix|refactor|test|docs|chore/<模块>-<动作>`；本地 pre-commit 拦 main 直提、pre-push 拦 main 直推；远程再开分支保护；里程碑在 main 上打注释 tag。
- **备选**：Git Flow（develop / release / hotfix 多长期分支）；主干开发（trunk-based）；只靠文档约定不做工具强制。
- **理由**：单人 3 天项目里 Git Flow 的长期分支是纯开销；只写文档约定等于没约定（工具拦不住的规则一定会破）；GitHub flow 是官方推荐且与 PR 机制天然契合。
- **代价**：每次改动多两步（开分支、开 PR），但换来可追溯的合并记录与干净的主干。
- **反馈**：待开发阶段验证——重点看"小改动是否被分支流程拖慢"，若拖慢则合并文档类改动到单个 `docs/` 分支。

## ADR-010 · 自动化沉淀分层：自动写事实 / AI 出草稿 / 人工签字

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：需求方要求提交时自动把记录沉淀进 `ai-session-log.md`、`testing.md`、`decisions.md`，并同步项目信息密度到 spec。
- **决策**：分三层——① 确定性事实（提交流水、测试登记、项目状态页）自动写入；② 判断性内容（影响面、规格补充建议、风险）由 LLM 出草稿到 `.ffshift/pending/`，人工采纳；③ `decisions.md` 与 `openspec/specs/` 只由人改。
- **备选**：让 AI 直接改三个文档（快，但会写进幻觉与错误结论，且面试官会怀疑文档真实性）；完全手工记录（真实但费时且容易漏）。
- **理由**：`decisions.md` 是决策档案、spec 是规格契约——被自动改写就失去可信度；而提交流水这类事实机器比人可靠。
- **代价**：草稿需要人工过一遍；带来一个额外产物目录需要管理。
- **反馈**：`scripts/sync-docs.mjs` 已实现；沉淀失败只写日志、不影响提交。
  踩坑留档：自动沉淀提交本身又触发了 post-commit，产生一串级联的 `docs: 自动沉淀` 提交（历史里保留，不重写）。
  修法是双保险——`post-commit` 与 `sync-docs` 各判一次"机器提交不触发沉淀"；机器提交也照样写正文、不绕开校验。

## ADR-011 · 引入 OpenSpec 做规格驱动开发

- **日期**：2026-09-22
- **状态**：已接受
- **背景**：需求方要求用 OpenSpec 初始化项目，并让后续改动及时沉淀到 spec 文档。
- **决策**：`openspec init`（v1.13.1，schema `spec-driven`，产物语言 zh-CN），生成 Claude Code / Cursor / Codex / GitHub Copilot / 通用 agents 五套指令；开发按 propose → apply → archive 流程，每个模块抽一个能力规格。
- **备选**：只在 `docs/` 手写规格；用 GitHub Issues 当需求台账；不引入任何规格层。
- **理由**：规格与变更分离（`specs/` 是现状、`changes/` 是提案），归档时会自动更新主规格，比手写文档更不容易失真；且能同时服务多个 AI 工具。
- **代价**：多一套目录与命令；规格写作有格式要求（Requirement / Scenario）。
- **反馈**：待开发阶段验证——重点是"三天里有没有时间真的走完一次 propose 到 archive 的完整流程"。

## ADR-012 · 文案约束接入 oil-tone

- **日期**：2026-09-22
- **状态**：已接受（原决策"用自拟契约替代缺失的 oil-tone"已由本决策取代）
- **背景**：需求方要求所有文档内容受 oil-tone 约束。首次核查时本机 `.agents/skills/` 只有 `oil-frontend`；随后需求方给出仓库地址 `github.com/oil-oil/oil-tone`。
- **决策**：克隆到 `~/.agents/skills/oil-tone`（其仓库把 skill 放在 `skills/oil-tone/` 子目录，已移到 skill 根目录以符合目录约定）；`scripts/lib/oil-tone.mjs` 负责定位并调用它的 `tone_lint.py`，pre-commit 对暂存的 Markdown 执行检查——FAIL 拦截、WARN 提示；`docs/writing-style.md` 保留为项目落地版（术语表、状态词）并注明上游。
- **备选**：把 tone_lint 的规则移植成 JS（自包含，但要跟着上游手工同步）；只在人工写文档时参考规范不做自动检查（等于没有约束力）。
- **理由**：同源调用能跟着 skill 更新走，且失败可跳过——它不在本机时项目照样能提交，不给协作者制造硬依赖。
- **代价**：依赖 python 与本机 skill 路径；换机器需要重装 skill。
- **反馈**：全量扫描 9 份文档，只有 1 处 FAIL（`decisions.md` 里的 `闭环` 属宣传黑话），已改。
  踩坑留档：接入后第一次试探提交没被拦住——`tone_lint.py` 在 Windows 上输出 CRLF，而解析函数按 `\n` 切行，行尾的 `\r` 让 `(.*)$` 永远匹配不上，检查静默失效；改成按 `\r?\n` 切行后正常。
  第二个坑：写作规则文档里"列出"禁词会被自己的规则拦下，禁词要用反引号或代码块包起来。
  单文件检查约 0.2s，全量 9 份文档不到 2s，放在 pre-commit 里不拖慢提交。

## ADR-013 · 样式用原生 CSS 变量，不引 Tailwind

- **日期**：2026-09-22
- **状态**：被 ADR-015 取代（2026-09-23）。当时的复评条件——"界面变多、样式开始重复时再引 Tailwind"——由外部需求触发，见 ADR-015。
- **背景**：设计系统已经把颜色、间距、圆角、动效定成 CSS 变量（`docs/design-system.md`）；应用当前只有一屏界面。
- **决策**：用手写 CSS + 变量实现，样式表单一文件；不引 Tailwind。
- **备选**：Tailwind v4（CSS-first 配置，能与设计系统变量共存）；Tailwind v3（成熟，但要额外配置文件与内容扫描）；CSS Modules（多一层文件管理）。
- **理由**：样式表不到 300 行，Tailwind 的收益（快速布局、强制一致性）在单屏界面里体现不出来，却多一个构建依赖和版本升级面；设计系统的变量本身就是约束，直接写更直观。
- **代价**：界面变多后样式复用要自己抽公共类；接手的人需要读 CSS 而不是查 Tailwind 文档。
- **反馈**：待界面数量明显增加、样式开始出现重复时复评；那时候再引 Tailwind 也不迟，现有变量可以原样保留。

## ADR-014 · 采用 v0.app 的三栏工作台布局与配色

- **日期**：2026-09-23
- **状态**：被 ADR-015 取代（2026-09-23）。"三栏骨架"这一条被保留下来，配色与组件配方整体换掉；"单一强调色、颜色只表达状态"仍然有效。
- **背景**：需求方给了一份 v0.app 生成的界面方案（Next.js + Tailwind + shadcn/ui），要求参考它的样式布局重构界面。原界面是单屏纵向流水线，设置、列表、动作挤在一列，信息密度低。
- **决策**：采纳它的三栏骨架（左设置 / 中队列 / 右详情）与四层底色配色；按本项目真实能力调整内容——左栏放批量设置与 AI 建议，右栏改成选中任务的媒体详情。
- **备选**：保留原单屏布局（已验证稳定，但密度低）；完全照搬 v0 产出（它的检查器里有编码器选择、CRF 滑块、音频与帧率下拉，后端根本没有这些能力，点下去只会骗用户）。
- **理由**：三栏是桌面工具的成熟形态，设置与内容分开符合用户预期；四层底色（canvas / panel / panel-soft / panel-raised）比原来的两级更适合区分面板、工作区与悬停态。
- **代价**：字号收了一档（正文 12px），可读性换信息密度；样式表从 7 KB 涨到 16 KB；引入 lucide-react 作为图标库（原计划用 Phosphor）。
- **反馈**：主按钮从"反白"改成"强调色实心"（v0 的做法）。为保证这条纪律不烂掉，把左栏的"添加视频"从主按钮降级为描边次级——全屏仍然只有"开始转换"一个主按钮。

## ADR-015 · 内化 EnsoCode 的设计语言，改用 Tailwind v4 + Base UI

- **日期**：2026-09-23
- **状态**：已接受。替代 ADR-013（样式用原生 CSS）与 ADR-014（v0.app 的配色与组件配方）；ADR-007 的立场条款与 ADR-014 的三栏骨架保留。
- **背景**：需求方要求"深度分析 [EnsoCode](https://github.com/J3n5en/EnsoCode)，参考它的样式排版彻底重构本项目，并把它的 UI 设计语言内化进来"。上一版界面（ADR-014）的底色分四层、主按钮是强调色实心，与 EnsoCode 不是同一套语言；两者混在一起会显得两头不靠。
- **决策**：整体换成 EnsoCode 的语言——
  ① 令牌层照抄它的语义命名与取值（OKLCH，中性色同色相 285.82，`--primary` 反白）；
  ② 技术底座跟它对齐：Tailwind v4（CSS-first，无配置文件）+ **Base UI**（不是 Radix）+ cva + tailwind-merge；
  ③ 组件层按它的配方重建（按钮/徽章/输入框/分段切换/下拉/对话框/提示/空态/进度条）；
  ④ 面层收敛到三档（`bg-background` 大面板 / `bg-muted` 及其半透明变体做嵌套与状态 / `bg-popover` 浮层），
     层级只由 1px 边框与半透明叠加表达；
  ⑤ 标题栏自绘（`frame: false`），因为窗口边框是系统灰条，会截断"所有面板同一个底色"。
- **备选**：
  - 保留纯 CSS、只把颜色和字号换成 EnsoCode 的值：改动最小，但组件配方（`active:scale-[0.97]`、`data-slot` 约定、变体表、半透明叠加）抄不过来，"内化语言"会退化成"换配色"；
  - 引入 EnsoCode 的全部原语（50 个 `ui/*.tsx`）：其中 `card`、`empty`、`meter`、`toolbar`、`sidebar` 在它自己仓库里都是零引用，抄过来就是抄来一堆没人维护的代码；
  - 引入 framer-motion 复刻它的侧栏 spring 动画：本项目只有一处动画用到，不值得多一个运行时依赖（ADR-008）。
- **理由**：设计语言说到底是"遇到一个结构时选哪种做法"的共识，只有连写法一起搬过来才能继续演化——后面加一个面板、一个状态，能直接照同类推。只对齐颜色的话，第一个新组件就会走回老路。
- **代价**：构建链多一个 Tailwind 插件与四个运行时依赖（`@base-ui/react`、`cva`、`tailwind-merge`、`clsx`）；全部标记与样式重写；端到端测试的定位锚点从类名换成 `data-slot`，`e2e/` 两个文件同步改；`docs/design-system.md` 与 `docs/ui-spec.md` 整体重写。
- **反馈**：
  - 对比度不是可以照抄的部分。上游暗色的 `--destructive`（`oklch(0.396 0.141 25.72)`）与 `--success`（`0.527 0.154 150.07`）是配白字做实心按钮用的，本项目拿它们当正文色时实测只有 1.97:1 与 4.01:1，低于 4.5:1 的硬线；换成 0.704 / 0.723 后是 6.85:1 与 8.70:1。这条已写进 `docs/design-system.md`，避免下次"对齐上游"时又改回去。
  - 尺寸也不能照抄。上游 `text-sm` 在 14px 根字号下是 12.25px，中文读得动；但它的 `badge` 最小一档在桌面宽度下是 10px，中文会糊成一团，本项目把徽章字号上调一档。
  - 底栏由"输入框 + 状态行"两条压成一条：本项目的主动作只作用于队列，照搬两条会空掉半行。
  - 保留的旧行为：`.ffshift`/`.queue-row` 那套类名换成 `data-slot`，端到端测试同步改；`npm run test:e2e` 9 条全绿（28.2s）。
